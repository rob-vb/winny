<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Create Play Console app + upload first .aab + configure service account</name>

  <what-built>
  The Android production .aab from Plan 03 is ready in EAS cloud. Google Play Console requires the first upload to be done manually — the Play Store API cannot create new app records. This is a one-time manual action. After the app record exists, eas submit handles all future uploads automatically.
  </what-built>

  <how-to-verify>
  Step 1 — Download the Android .aab from EAS:
    eas build:list --platform android --limit 3
    (Copy the download URL for the most recent finished production build)
    eas build:download --id <build-id>
    (Or download from https://expo.dev/accounts/robvb/projects/winny/builds)

  Step 2 — Create app in Google Play Console:
    1. Open https://play.google.com/console
    2. Click "Create app"
    3. Fill in:
       - App name: Winny
       - Default language: English
       - App or game: App
       - Free or paid: Free
    4. Accept declarations and click "Create app"

  Step 3 — Set up Internal Testing release:
    1. Go to Release → Testing → Internal testing
    2. Click "Create new release"
    3. Upload the .aab from Step 1
    4. When prompted for signing: select "Use Google Play's app signing" (Play manages the upload key — matches D-12 managed signing approach)
    5. Release name: 1.0.0 (or auto-assigned)
    6. Click "Save" then "Review release" then "Start rollout to internal testing"

  Step 4 — Create Google Service Account for eas submit:
    1. Open https://console.cloud.google.com
    2. Select the project linked to your Play Console account (or create a new one)
    3. Navigate to IAM & Admin → Service Accounts → Create Service Account
    4. Name: eas-submit (or any name)
    5. Create and download a JSON key
    6. Save the downloaded JSON key as "google-service-account.json" in the project root directory (/Users/rob/Development/winning-streak/google-service-account.json)
    7. DO NOT commit this file — it is already in .gitignore from Plan 01. Verify: git status (file should show as ignored, not staged)

  Step 5 — Grant service account permissions in Play Console:
    1. In Play Console → Users and permissions → Invite new users
    2. Enter the service account email (from the JSON key file: client_email field)
    3. Grant role: "Release manager" permission
    4. Click Apply

  Step 6 — Confirm these two things before resuming:
    A. The .aab is uploaded and the Internal Testing release status shows "In review" or "Available to testers"
    B. google-service-account.json exists in the project root but is NOT staged in git (run: git status; the file should appear under "Ignored files" or not appear at all)
  </how-to-verify>

  <resume-signal>Type "done" when all 6 steps are complete and both confirmations (A and B) are verified. Note the Play Console app package name shown in the console (should be com.robvb.winny) and whether it matched or needed adjustment.</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| google-service-account.json → Google Play API | Service account key is a bearer credential; full Release Manager access to Play Console |
| Play Console API → public store | Releases promoted via API have immediate public visibility once rolled out |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-13 | Information Disclosure | google-service-account.json credential leak | mitigate | File is in .gitignore (Plan 01); Task 3 automates verification that file is not tracked; rotate key immediately if committed accidentally |
| T-07-14 | Elevation of Privilege | Service account with Release Manager role | accept | Release Manager role is the minimum required for eas submit; avoid Owner or Admin roles for the service account |
| T-07-15 | Denial of Service | Google Play 14-day tester gate (new accounts) | accept | Gate is policy-enforced by Google; no mitigation possible — plan for it; start closed testing on day 1 if gate applies |
| T-07-16 | Tampering | First .aab upload to wrong track | mitigate | Upload to Internal Testing (D-11), not Production — internal track limits blast radius if binary has issues |
</threat_model>
